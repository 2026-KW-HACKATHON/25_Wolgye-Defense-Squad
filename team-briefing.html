01 / OUR DECISION

작은 실제 흐름 하나를 완성한다

공개 전략

02 / WHY THIS PRODUCT

지역 문제에서 기능까지 연결한다

검증할 가설: 학생·주민은 예산과 취향에 맞는 골목 가게를 찾기 어렵고, 소상공인은 해당 손님에게 메뉴 정보를 전달하기 어렵다. 아직 확인된 사실이나 통계가 아니다.

문제 가설요구사항기능·화면검증 방법
검색 후 가격을 다시 확인한다예산 충족 여부와 근거메뉴 가격·출처·확인일가격 일치율 확인
여러 명의 취향 합의가 어렵다함께 선택할 후보와 이유후보 3곳·공유·투표결정 시간 비교
조건에 맞는 골목 가게를 모른다적합한 지역 가게 발견조건 충족 후보 내 지역 가게 우선처음 알게 된 가게 비율

초기 조사 목표: 학생·주민 5~8명, 상인 2~3명. 대표 통계가 아닌 탐색적 인터뷰로 제시한다.

03 / SCORING STRATEGY

중간과 최종은 준비의 중심이 다르다

중간 기준배점준비할 증거
논리의 연결성30문제 → 요구사항 → 정책 → 화면 연결표
실현·상용화 가능성20작동 데모, 데이터 확보 방식, 운영 주체·비용 가정
문서 재현 가능성20API 계약, 필터·정렬 기준, 예외 처리
창의성·차별성20근거 있는 지역 가게 발견과 공동 결정 경험
발표10하나의 사용자 상황으로 이어지는 설명

최종 배점: 실현·상용화 30 / 구현·기술력 20 / 지역 적합성 20 / 차별성 20 / 발표 5 / 참여도 5. 실제 사용 가능성과 지역 문제 해결의 증거에 우선 투자한다.

공식 홈페이지 기준 전시 진출은 심사위원·팀 상호평가 2:1 합산, 상위 15팀. 전달된 Discord 공지는 10~15팀으로 표현한다. 주민투표는 이후 합산되며 정확한 환산 방식은 추가 확인이 필요하다. 중간점수의 최종 합산은 제공 공지에 명시되지 않았다.

04 / DISTINCTIVE IDEAS

추가 아이디어: 구현 가치가 큰 순서로

아래는 차별화 후보이며, 시장의 독점적 기능임을 검증한 주장은 아니다. 중간 이후 사용자 반응으로 우선순위를 조정한다.

우선 제안 · 중간부터

근거가 보이는 한 끼

‘추천합니다’와 함께 어떤 메뉴 가격을 근거로 예산에 맞췄는지 보여준다. 실제 데이터 연결 후 출처·확인일·미확인 항목을 표시한다.

현재: 업종 추정 가격임을 표시. 이후: 실제 데이터 검증과 갱신.

핵심 정책 · 중간부터

조건을 지키는 골목 발견

예산·취향을 먼저 충족한 후보 안에서 소상공인을 우선한다. 후보가 부족해도 무관한 가게로 세 곳을 채우지 않는다.

현재: 일부 프랜차이즈 제외로 지역 가게 후보 추정. 실제 판별 기준은 합의 필요.

최종 후보

모두의 한 끼 합의

공유 링크에서 각자의 예산·싫어하는 메뉴를 받고 공통 후보로 투표한다. 공통 후보가 없으면 어떤 조건이 충돌하는지 설명한다.

범위: 웹 투표 우선. 외부 메신저 내부 투표 연동은 별도 검증.

보류 후보: 상인의 ‘오늘 가능한 한 끼’

상인이 오늘의 메뉴·가격·품절을 직접 갱신하는 간단한 화면. 정보 신뢰도와 운영 가능성을 높일 수 있지만, 실제로 갱신할 의사가 있는 상인을 확인한 뒤 개발한다. 실시간 재고나 좌석을 추정해서 표시하지 않는다.

05 / CURRENT IMPLEMENTATION

팀원 앱 기반 통합 검토본

React 대화 화면·식당 카드·Express 서버·카카오 장소 및 블로그 검색·NVIDIA 소개 문구 생성을 통합했다. 실제 키를 사용한 동작은 별도 검증이 필요하다.

조건 추출은 정규식이며 가격·시간·지역 가게 분류는 추정이다. 로그인은 시뮬레이션, 공유는 기기 공유창 또는 문구 복사, 일정은 작성 화면 열기다.

실제 메뉴 가격 검증, RAG, 공동 투표, 카카오 인증·전용 공유 SDK는 미구현이다. 개발 현황은 검증된 범위만 작성한다.

07 / WORKING TOGETHER

공통 기반 하나, 작은 기능 브랜치 여러 개

setup 브랜치 → PR → main → 기능별 브랜치 → 검토 → main

담당 영역: 화면 / 서버·데이터 / 추천 / 공유·배포. 인원에 따라 겸임한다. 역할별 장기 브랜치 대신 request-form, recommendation, share-vote처럼 작은 작업으로 분리한다.

  • Issue에 담당자·범위·완료 기준을 쓴다.
  • 공통 데이터 형식과 API 변경은 먼저 공유한다.
  • PR에 실행 방법·확인 결과·미구현 범위를 적는다.
  • main은 실행 가능한 상태를 유지하고, 매일 전체 흐름을 확인한다.
  • 키와 비밀번호는 저장소에 올리지 않는다.

공통 기반은 chore/demo-foundation 브랜치에서 준비한다. 팀 검토 후 PR로 main에 반영하며, 이후 팀원들은 최신 main에서 각자 기능 브랜치를 만든다.
