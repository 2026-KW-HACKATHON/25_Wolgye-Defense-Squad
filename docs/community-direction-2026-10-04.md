# 월계1동 상권 커뮤니티 구현 제안

2026-10-04. 목적은 사용자 확정 방향, 기술과 운영 정책은 검토용 제안. 기능 구현 완료 기록이 아니다.

## 사용자 목적과 고민
- 궁극적인 목표는 월계1동 상권 활성화를 위한 커뮤니티. 주민·방문자·사장님이 최신 가게 정보를 공유하고 골목 가게를 발견한다.
- 이 데이터를 이용해 가족모임·친구와의 만남·혼자 조용한 식사 등 목적별 장소를 추천하고 기존 카카오 초대 그룹 추천·투표도 유지한다.
- 사용자는 AI 검색에서 광고성·오래된 정보가 나오는 경험을 했고 무료 AI에서 특히 아쉬웠다고 설명했다. 일반적인 무료/유료 AI 정확도 차이가 검증됐다는 의미는 아니다.
- 타이핑이 어려운 사람을 위한 음성 입력과 간결하고 고급스러운 UI를 희망. Streamlit 제외.

## 핵심 구조 제안
가게별 커뮤니티 제보 → 확인·구조화 → 출처와 관찰 시각을 갖춘 가게 정보 → 목적별/그룹 추천 → 방문 → 정보 재확인.
- 홈: 동네 최신 소식, 장소 찾기, 정보 올리기. 추천과 글쓰기 모두 음성·텍스트·버튼 지원.
- 글: 자유 게시판보다 가격·메뉴/영업 변경/새 가게/시설/방문 경험으로 분류하고 가게와 연결.
- 데이터: places, observations, evidence, current_facts, posts, groups, preferences, votes. 변경 전후와 승인 이력을 보존하고 같은 값도 재확인 이력을 남긴다.
- 사실별로 값, 관찰 시각, 등록 시각, 작성 주체, 근거, 확인 상태, 만료 정책을 저장. 최신 글 작성일과 실제 방문일을 구별한다.
- 소음·분위기는 시간대별 경험이며 객관적 보장으로 표시하지 않는다. 사장님 확인과 방문자 확인도 구별한다.
- 신규 장소는 핀·이름·간판/메뉴판 사진으로 제안하고 중복과 실재 확인 후 반영. 미확인은 별도 표시. 공식 사업장 등록이나 소유자 인증을 대체하지 않는다.
- 확인 대기/반영/분쟁/오래됨 상태, 신고·되돌리기, 검증된 기여 보상. 계정 수만으로 검증하지 않으며 광고·이해관계를 표시한다.
- 가게 20~30곳을 팀이 먼저 조사하고 소수 사장님과 파일럿 진행하는 방안. 참여·최신성을 사용자가 처음부터 채우길 기대하지 않는다.

## 추천과 음성
- LLM: 자연어 의도·조건 구조화, 모호한 부분 확인, 근거 기반 설명. DB가 후보와 사실의 원천이며 존재하지 않는 가게·메뉴를 생성하지 않음.
- 필수 조건 먼저 검사, 목적 적합도·신선도·증거 품질로 정렬. 미확인은 충족으로 처리하지 않음. 출처 없는 조건은 확인 필요로 표시.
- SQL 필터와 태그부터 구현. 리뷰 의미 검색이 필요할 때만 임베딩/검색 증강 추가. 최신 상태·만료·권한은 검색 증강만으로 해결되지 않음.
- STT(음성→문자) → 변경안/검색 조건 카드 → 사용자 확인 → 저장 또는 추천. TTS(문자→음성)는 확인 내용을 읽어주는 선택 기능.
- 음성 인식 API는 한국어 가게명·가격·소음 환경 실측 후 결정. 서버 STT 우선 검토, 브라우저 음성 인식만 의존하지 않음. 오디오 저장 최소화, 마이크 사용 안내와 텍스트 대안 제공.
- 카카오 공유는 사용자가 초대 링크를 보내는 흐름이며 공동 상태는 DB로 관리. 자동 예약은 초기 범위에서 제외하는 제안.

## 기술 제안과 근거
- 현재 package.json: React/Vite/Tailwind/Express. UI를 Python으로 작성해야 하는 기술적 필요는 없음.
- 우선안: 기존 React UI와 Express 유지, 공용 PostgreSQL·사진 저장·권한을 추가. Python AI 처리가 필요할 때 FastAPI 서비스로 분리하되 동일 책임의 서버를 중복 개발하지 않음.
- Python 서버를 주력으로 정한다면 React + FastAPI로 API를 일원화하는 별도 전환 계획. UI까지 Python 필수라면 Reflex 후보. 아직 전환 결정 아님.
- [Reflex](https://reflex.dev/docs/advanced-onboarding/how-reflex-works/): Python으로 정의한 UI를 React로 변환, CSS·커스텀 컴포넌트 지원. 기존 코드 이전 비용과 지도·녹음 연동은 검토 필요.
- [NiceGUI](https://github.com/zauberzeug/nicegui): Python 브라우저 UI, HTML·Tailwind 지원. 관리자 검토 화면 후보.
- [FastAPI](https://fastapi.tiangolo.com/): Python API 서버 후보.
- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): DB 채택 시 그룹·작성자·소유자·운영자별 권한 정책 적용. 클라이언트 버튼 숨기기로 권한을 대신하지 않음.
- [브라우저 SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition): 지원 환경 차이 확인 필요.
- [NVIDIA ASR](https://docs.nvidia.com/nim/speech/latest/reference/api-references/asr/index.html): NIM 음성 기능 존재. 현재 NVIDIA Build 계정에서 원하는 한국어 모델이 호스팅 제공되는지와 비용은 별도 검증; LLM 키만으로 음성이 된다고 가정하지 않음.

## 구현 순서와 검증
1. 실제 가게 데이터, 공용 DB, 수정 제안·확인·이력·운영자 검토.
2. 최신 소식과 가게 상세, 근거를 보여주는 개인 목적 추천.
3. STT 변경안 확인, 실제 다중 기기 그룹 초대·투표.
4. TTS·알림·기여 보상·사진 인식·예약 보조 순으로 확장 검토.
- 대표 시연: 사장님 음성으로 가격 변경 제안 → 확인 → 다른 기기에서 출처·확인일 표시 → 예산 추천 결과 갱신 → 그룹 공유·투표.
- 테스트: 잘못 들은 가격 수정, 미확인 조건, 상충 제보, 만료 정보, 중복 장소, 권한 없는 변경, 여러 기기 투표, 추천 근거 일치.
- 상권 지표: 신규 가게 발견·저장·길찾기·전화·실제 방문을 구분, 검증된 정보 갱신 및 재기여율. 클릭을 방문/매출로 간주하지 않음.
- 네이버 대비 표본 최신성·누락 여부를 날짜와 범위 포함해 비교하고, AI 대비 동일 질의의 실제 영업/가격/시설 일치율·근거 제시율을 측정. 우수성은 결과 확보 후 주장.
