# 월계밥상 사전연구 및 예약 연동 검토

조사일: 2026-09-28. 제안 단계이며 API 도입이나 효과 검증이 완료된 것은 아니다.

## 사용자의 질문

사전연구·background의 근거를 보강하고, arXiv MCP 활용 가능 여부와 catchtable-cli를 통한 대기시간·예약 정보 연동을 검토해 달라는 요청이다. 현재 연결 도구에는 arXiv 전용 MCP가 없어 웹에서 원문 페이지를 확인했다.

## 선행연구

- Carl Anderson (2018), [A survey of food recommenders](https://arxiv.org/abs/1809.02862). arXiv 프리프린트. 음식·식당 추천의 데이터, 접근법, 제약을 정리한다. 음식 추천 자체의 신규성을 주장하기보다 그룹 조건과 현장 정보 연결에 초점을 둘 근거. 초록 확인.
- Stratigi et al., [Sequential group recommendations based on satisfaction and disagreement scores](https://link.springer.com/article/10.1007/s10844-021-00652-x). 온라인 공개 2021, 학술지 권호 2022. 그룹 만족도와 구성원 사이의 만족도 편차, 이전 추천 이력을 고려한다. 우리 서비스에는 필수 조건을 먼저 지키고 특정 사람만 반복적으로 양보하지 않도록 설계하는 데 참고. 식당 서비스의 효과를 직접 입증한 것으로 쓰지 않는다.
- Goodchild (2007), [Citizens as sensors: the world of volunteered geography](https://link.springer.com/article/10.1007/s10708-007-9111-y). GeoJournal. 시민이 지역 정보를 생산·보완하는 VGI 개념과 참여 동기·정확성 문제를 논한다. 메뉴판 사진·가격·확인 날짜·수정 이력 설계의 개념적 배경. 공개 초록 확인; 월계동 정보 부족의 실증 근거는 아니다.

## 관련 서비스

- [Doodle](https://help.doodle.com/en/articles/9457227-do-i-need-a-doodle-account-to-participate-in-a-group-poll): 초대 링크로 참여해 응답하고 그룹 결정을 돕는 방식. 빠른 그룹 참여와 투표 UX 참고.
- [Google Local Guides](https://support.google.com/maps/answer/6304221?hl=EN): 사진·정보 수정·장소 추가 등 기여와 포인트. 기여 결과와 보상 참고. 검증된 수정과 최신성에 보상하는 방안 제안.
- [네이버 신규 장소 제보](https://help.naver.com/service/30026/contents/20467?osType=COMMONOS): 기존 지도에도 신규 장소 제보가 있다. '기존 지도는 사용자 등록 불가' 또는 검증 없이 '네이버보다 쉽다'고 주장하지 않는다.
- [캐치테이블 비즈](https://biz.catchtable.co.kr/n/main): 예약·웨이팅 운영 서비스. 공식 서비스의 기능과 비공식 CLI 지원 범위는 별개다.

## catchtable-cli 검토

- [README](https://github.com/tellang/catchtable-cli): 공식 제휴 없는 비공식 도구이며 비공식 엔드포인트 변경으로 중단 가능하다고 명시한다. MIT 표기와 별개로 README에 연구·개인 목적 및 용도 제한 문구가 있어 공개 서비스 적용 전 제공자 허용 범위 확인이 필요하다.
- [client.py](https://raw.githubusercontent.com/tellang/catchtable-cli/main/catchtable_cli/client.py): 검색, 매장·메뉴, 예약 가능 날짜·시간, 예약 생성·목록 요청 코드가 존재한다. 인증은 세션 쿠키 기반이다. 대기 팀 수·예상 대기분 전용 조회는 확인되지 않았다.
- 문서·코드 읽기만 수행했다. 설치·로그인·API 호출·예약 실행은 하지 않았으며 실제 작동, 월계동 매장 포함률, 응답 필드는 미검증이다.
- 제안: 월계동 표본 매장의 포함률과 날짜·인원별 조회 품질부터 검증한 뒤 보조 데이터로 채택 여부 결정. 사용자에게 예약 완료를 표시하는 기능은 별도 구현·검증 대상이다.

## 제안하는 서비스 흐름

그룹 구성 → 자연어 조건 확인 → 지역 메뉴·가격으로 후보 선별 → 제공 가능한 예약·혼잡 정보 보완 → 최대 3개 후보 투표 → 선택 매장의 최신 상태 재확인 → 외부 예약 페이지/전화 연결 → 방문 후 정보 갱신.

- 총 소요시간 = 왕복 이동 + 입장 대기 + 주문·조리·식사 + 여유 시간. 예약 입장까지의 대기와 현장 줄서기를 중복 합산하지 않는다.
- 알 수 없는 대기시간은 0분으로 넣지 않는다. 시간 제한을 만족한다고 확정할 수 없으면 '시간 조건 확인 필요'로 구분한다.
- 대기 팀 수는 대기분과 다르다. 인원·좌석·회전 속도 데이터 없이 분으로 단정하지 않는다. 예약 가능도 즉시 입장이나 예약 확정을 뜻하지 않는다.
- LLM은 조건 해석과 확인 질문을 담당한다. 실시간 대기시간을 생성하게 하지 않는다.
- 미입점 골목 가게도 추천 대상에 남기되 영업·메뉴 정보의 출처와 확인일을 표시하고 전화 확인을 제공한다.
- 초기 제안: 사장님이 '바로 입장/약 10~20분/만석'과 확인 시각을 직접 갱신. 이용자 제보는 별도 출처로 표시하고 오래된 혼잡 정보는 만료한다. 아직 구현·합의되지 않은 아이디어다.

## 발표 근거 보강 계획

- Problem 1: 조건이 다른 구성원의 합의 부담. 그룹 추천 연구를 배경으로 인용하고 광운대 학생 모임 인터뷰로 지역 문제를 확인한다.
- Problem 2: 가게 존재 여부뿐 아니라 메뉴·가격·영업 정보의 부족·오래됨으로 선택이 어려울 가능성. 현장 조사 전에는 가설로 표시한다.
- 조사 제안: 가게 20곳의 지도 등록·메뉴·가격·현장 일치 여부 기록, 학생 모임 5팀의 최근 식당 결정 과정과 소요시간 인터뷰. 수치는 조사 목표이지 결과가 아니다.
- 평가 제안: 결정 시간, 처음 알게 된 가게의 후보 포함·선택·실제 방문, 검증된 정보 수정 수. 매출 증가는 매출 자료를 얻기 전까지 기대 효과로만 표현한다.
- 후보 3개는 현재 UX 선택이며 위 연구가 최적 개수로 입증한 것은 아니다.
